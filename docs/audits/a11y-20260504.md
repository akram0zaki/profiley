# Profiley Accessibility Audit Report

**Date:** 2026-05-04
**Scope:** Full frontend application (`apps/frontend/`)
**Standard:** WCAG 2.2 Level AA
**Methodology:** Manual code review of all pages, components, styles, and UI patterns

---

## Executive Summary

Profiley demonstrates solid baseline accessibility through its use of Radix UI primitives (which provide built-in keyboard interaction, focus management, and ARIA attributes for complex widgets). Semantic HTML landmarks (`<header>`, `<nav>`, `<main>`, `<footer>`) are used correctly. The app ships with RTL support for Arabic and applies `document.documentElement.dir` / `lang` dynamically.

However, significant gaps exist in keyboard navigation, screen-reader announcements, focus management, color contrast, and form labeling. These are detailed below, organized by severity and category.

**Compliance score estimate:** ~60% of WCAG 2.2 AA criteria partially or fully met; ~15 critical/high-severity items identified.

---

## 1. Missing Skip Navigation Link — CRITICAL

**WCAG Criterion:** 2.4.1 Bypass Blocks (Level A)
**Files affected:** `index.html`, `app-layout.tsx`, all page layouts

There is no "Skip to main content" link anywhere in the application. Keyboard-only and screen-reader users must tab through the entire header navigation on every page before reaching the main content.

**Current state:**
- `index.html` has no skip link
- No skip-link component exists
- `<main>` element exists but has no `id` to serve as a skip target

**Recommended fix:**
Add a visually hidden skip link as the first focusable element in the DOM that becomes visible on focus:

```html
<a href="#main-content" class="sr-only focus:not-sr-only focus:absolute focus:top-4 focus:left-4 focus:z-[100] focus:px-4 focus:py-2 focus:bg-primary focus:text-primary-foreground focus:rounded">
  Skip to main content
</a>
```

Add `id="main-content"` to the `<main>` element in `App.tsx`.

## 2. Page Title Not Updated on Route Changes — CRITICAL

**WCAG Criterion:** 2.4.2 Page Titled (Level A)
**Files affected:** `index.html`, all page components

`index.html` has a static `<title>Profiley — Let Your Experience Speak</title>`. This title never changes when the user navigates between pages. Screen-reader users rely on the page title to understand where they are.

**Current state:**
- No `<title>` management hook or component exists
- No per-page title metadata
- SPA route changes do not update `document.title`

**Recommended fix:**
Create a `useDocumentTitle` hook and use it in each page:

```tsx
// hooks/use-document-title.ts
import { useEffect } from 'react';
export function useDocumentTitle(title: string) {
  useEffect(() => {
    const prev = document.title;
    document.title = `${title} — Profiley`;
    return () => { document.title = prev; };
  }, [title]);
}
```

Apply in every page component:
```tsx
// e.g., dashboard.tsx
useDocumentTitle(t('dashboard.title'));
```

## 3. No Focus Management on SPA Route Changes — CRITICAL

**WCAG Criterion:** 2.4.3 Focus Order (Level A)
**Files affected:** `scroll-to-top.tsx`, all page transitions

When navigating between routes via React Router, focus remains wherever it was (often on the clicked link). The viewport scrolls to top but focus does not move to the new page heading. Screen-reader and keyboard users get no indication that navigation completed.

**Current state:**
- `ScrollToTop` only calls `window.scrollTo()`, no focus management
- No ref forwarding to page headings

**Recommended fix:**
Extend `ScrollToTop` or create a route-change hook that moves focus to the `<main>` element or to the `<h1>` after navigation:

```tsx
useEffect(() => {
  window.scrollTo({ top: 0, left: 0, behavior: 'auto' });
  // Move focus to main content
  const main = document.querySelector('main');
  if (main) {
    main.setAttribute('tabindex', '-1');
    main.focus({ preventScroll: true });
  }
}, [location.pathname]);
```

## 4. SimpleDropdown Is Not Keyboard Accessible — CRITICAL

**WCAG Criteria:** 2.1.1 Keyboard, 4.1.2 Name/Role/Value (Level A)
**File affected:** `components/simple-dropdown.tsx`

The custom `SimpleDropdown` component is used for the user menu, language selector, and theme toggle dropdown on the landing page. It is NOT keyboard accessible and has NO ARIA semantics.

**Current gaps:**
- Trigger is a `<div onClick>` — not focusable, not a `<button>`
- No `aria-haspopup`, `aria-expanded`, `role="menu"`, `role="menuitem"`
- No keyboard handlers (Escape to close, Arrow keys to navigate items)
- No focus trap within the open dropdown
- Click-outside uses `mousedown` only — doesn't handle keyboard dismissal
- `SimpleDropdownItem` is a `<div onClick>` — not focusable

**Recommended fix:**
The dropdown is used for navigation menus, language selection, and user account actions. Replace with either:
1. Radix UI `DropdownMenu` (already available in `components/ui/dropdown-menu.tsx`) which provides full keyboard and ARIA support
2. Or retrofit `SimpleDropdown` with proper button triggers, ARIA roles, and keyboard handling

## 5. Icon-Only Buttons Missing Accessible Names — HIGH

**WCAG Criterion:** 4.1.2 Name, Role, Value (Level A) / 2.5.5 Target Size
**Files affected:** `app-layout.tsx`, `landing.tsx`, `legal-layout.tsx`, `uploads.tsx`

Several icon-only buttons lack `aria-label`, making them invisible to screen readers.

**Specific instances:**
| Location | Button | Has aria-label? |
|---|---|---|
| `app-layout.tsx` | Theme toggle (Sun/Moon) | **NO** |
| `app-layout.tsx` | Mobile menu toggle (Menu/X) | **NO** |
| `landing.tsx` | Theme toggle (Sun/Moon) | **NO** |
| `app-layout.tsx` | Language selector trigger | **NO** |
| `uploads.tsx` | Delete document button | Yes: `t('uploads.list.deleteAria')` |
| `legal-layout.tsx` | Theme toggle | Yes: `"Toggle theme"` |

**Recommended fix:**
Add `aria-label` to every icon-only button. Use translation keys:

```tsx
// Theme toggle
<Button aria-label={t('a11y.toggleTheme')} ...>

// Mobile menu
<Button aria-label={t('a11y.toggleMenu')} ...>

// Language selector
<Button aria-label={t('a11y.selectLanguage')} ...>
```

Additionally, icon-only buttons use `size="icon"` which renders at 36×36px (`size-9`). For WCAG AAA touch target compliance (44×44px), consider increasing to `size-10` (40×40px) or `size-11` (44×44px).

## 6. Color Contrast Deficiencies — HIGH

**WCAG Criterion:** 1.4.3 Contrast (Minimum) (Level AA)
**Files affected:** `theme.css`, `tailwind.css`, all components using `text-muted-foreground`

The design system defines muted text colors that likely fail WCAG AA contrast ratios.

**Specific issues:**

| Token | Light mode value | Dark mode value | Contrast concern |
|---|---|---|---|
| `--muted-foreground` | `#717182` (≈4.3:1 on white) | `oklch(0.708 0 0)` (≈5.1:1 on near-black) | Borderline at small sizes |
| `text-muted-foreground` used for helper text | Many instances | Many instances | Needs ≥4.5:1 for normal text |
| Gradient text (`bg-clip-text text-transparent`) | Brand gradient | Brand gradient | Gradient text has no contrast guarantee |
| `--primary` (dark mode) | N/A | `oklch(0.985 0 0)` on `oklch(0.145 0 0)` | Very high contrast — good |
| `--destructive` | `#d4183d` | `oklch(0.396 0.141 25.723)` | Verify ≥4.5:1 on backgrounds |

**Recommended fix:**
1. Darken `--muted-foreground` in light mode from `#717182` to at least `#595969` (≈5.5:1)
2. Darken `--muted-foreground` in dark mode from `oklch(0.708 0 0)` to `oklch(0.65 0 0)` (≈6:1)
3. Add a contrast-check step to CI using a tool like `axe-core` or `pa11y`
4. For gradient text on landing hero, ensure the fallback (non-gradient) color meets contrast

## 7. No Reduced Motion Support — HIGH

**WCAG Criterion:** 2.3.3 Animation from Interactions (Level AAA) / Prefers-reduced-motion
**Files affected:** `tailwind.css`, all animated components

The app uses Tailwind's `animate-in`, `animate-out`, `fade-in`, `zoom-in`, `slide-in-from-*` classes extensively (dialogs, select dropdowns, toasts, tooltips, accordion, collapsible). There is no `prefers-reduced-motion` media query anywhere.

**Current state:**
- No `@media (prefers-reduced-motion: reduce)` in any CSS file
- Tailwind `motion-safe:` / `motion-reduce:` prefixes not used
- Animations run regardless of OS-level accessibility settings

**Recommended fix:**
1. Add to `tailwind.css` or `index.css`:
```css
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
  }
}
```
2. Or wrap animation classes with `motion-safe:` prefix (e.g., `motion-safe:animate-in`)

## 8. Chat Interface Lacks Screen-Reader Announcements — HIGH

**WCAG Criterion:** 4.1.3 Status Messages (Level AA)
**File affected:** `components/chat-interface.tsx`

The chat interface is a core feature. When new messages arrive, a screen-reader user has no way of knowing unless they manually navigate the message list.

**Current gaps:**
- Message container (`div.flex-1.overflow-y-auto`) has no `role="log"`, `aria-live`, or `aria-relevant`
- New messages are appended to state but not announced
- Typing indicator has no accessible label
- Error messages appear in the UI but are not announced
- Cooldown timer state has no ARIA feedback
- Citations rendered as `<span title="...">` — `title` attribute is unreliable for screen readers

**Recommended fix:**
1. Wrap message list in an ARIA live region:
```tsx
<div role="log" aria-live="polite" aria-relevant="additions" aria-label={t('chat.conversationAria')}>
```
2. Announce typing state with `aria-live="polite"` region
3. Announce errors with `role="alert"`
4. Replace `title` on citation spans with proper accessible descriptions

## 9. Form Inputs Missing Visible Labels — HIGH

**WCAG Criterion:** 1.3.1 Info and Relationships / 3.3.2 Labels or Instructions (Level A)
**Files affected:** `job-fit-preview.tsx`, `uploads.tsx`, `profile.tsx`, `onboarding.tsx`, `public-profile.tsx`

Several inputs rely solely on `placeholder` text rather than proper `<Label>` components.

**Specific instances:**
- `job-fit-preview.tsx`: Job title, company name, and job description inputs have `placeholder` but no visible `<Label>`
- `public-profile.tsx`: Contact form inputs (name, email, message) — need to verify label presence
- `uploads.tsx`: The file input is hidden (`<input ref={inputRef} type="file" className="hidden" />`) and triggered by a `<Button>`. While this pattern is common, the button should have `aria-label` describing the action.
- `knowledge.tsx`: Search input has an icon (`Search`) but no visible label — only `placeholder="Search knowledge base..."`

**Recommended fix:**
- Add `<Label htmlFor={id}>` for every input, even if visually hidden via `sr-only` for aesthetic reasons
- For the file upload button: add `aria-label={t('uploads.selectFile')}` 
- For search inputs: use `aria-label` or a visible label

## 10. No Error Summary on Form Submission — MEDIUM

**WCAG Criterion:** 3.3.1 Error Identification / 3.3.3 Error Suggestion (Level AA)
**Files affected:** `login.tsx`, `onboarding.tsx`, `profile.tsx`, `settings.tsx`, `job-fit-preview.tsx`

When form validation fails or API errors occur, errors are shown as toast notifications (`toast.error()`) but are not rendered inline near the offending field with `aria-describedby` links.

**Current state:**
- Login errors set as `error` state and rendered in a `<p>` — but not linked to the email input
- Onboarding uses toast-only error feedback
- Profile save uses toast-only error feedback
- Job fit analysis uses toast-only error feedback
- The `Form` component (react-hook-form + Radix) has proper `aria-describedby` support — but it's only used if developers explicitly use `<FormMessage />`

**Recommended fix:**
1. For API-driven forms: render errors inline near the relevant field and associate with `aria-describedby`
2. For toast notifications: add `role="alert"` to the sonner toast container
3. When form validation fails, move focus to the first error

## 11. Progress Bar Missing Accessible Name — MEDIUM

**WCAG Criterion:** 4.1.2 Name, Role, Value (Level A)
**File affected:** `components/ui/progress.tsx`

The `Progress` component wraps `@radix-ui/react-progress` but does not forward `aria-label`, `aria-labelledby`, or `aria-valuetext`. Radix ProgressPrimitive supports `getValueLabel` but it's not exposed.

**Current state:**
```tsx
<Progress value={progress} className="h-2" />
```
No accessible name. Screen readers may announce "progress bar 50 percent" without context.

**Recommended fix:**
Expose `aria-label` and `aria-labelledby` props on the `Progress` component and pass them to `ProgressPrimitive.Root`. Add `aria-label` to every usage:

```tsx
<Progress value={progress} aria-label={t('onboarding.progressAria')} />
```

Also expose a `getValueLabel` prop:
```tsx
<ProgressPrimitive.Root getValueLabel={(value) => `${value}% complete`} ... />
```

## 12. Toast Notifications Not Announced to Screen Readers — MEDIUM

**WCAG Criterion:** 4.1.3 Status Messages (Level AA)
**File affected:** `components/ui/sonner.tsx`

The `Toaster` component from `sonner` renders toast notifications, but there's no explicit `role="status"` or `aria-live` region configured. Sonner defaults may provide some accessibility, but this should be verified and explicitly configured.

Configure sonner with explicit accessible options:

<Sonner

## 13. Heading Hierarchy Issues — MEDIUM

**WCAG Criterion:** 1.3.1 Info and Relationships (Level A) / 2.4.6 Headings and Labels (Level AA)
**Files affected:** Multiple page components

Heading levels should form a logical, nested outline. Several issues were identified:

**Specific instances:**
- `dashboard.tsx`: Stat cards use `<CardTitle>` (renders as `<h3>`) directly under the page `<h1>` — correct
- `landing.tsx`: Feature cards use `<CardTitle>` (`<h3>`) — but are they nested under an `<h2>`? The hero `<h1>` is followed directly by card `<h3>` elements without an `<h2>` section heading
- `onboarding.tsx`: Step content uses `<h2>` inside a `<CardContent>` which is correct under the page `<h1>`
- `chat-interface.tsx`: No heading structure at all within the chat area
- `knowledge.tsx`: Stat cards have `<CardTitle>` as `<h3>` — missing a section `<h2>`

**Recommended fix:**
1. Audit every page for a single `<h1>`, logical `<h2>` sections, and `<h3>` subsections
2. Add section headings (`<h2>`) on landing page between hero and feature cards
3. Add `aria-level` where heading semantics are implicit (e.g., card titles)

## 14. Loading States Lack Accessible Text — MEDIUM

**WCAG Criterion:** 4.1.3 Status Messages (Level AA)
**Files affected:** `dashboard.tsx`, `settings.tsx`, `knowledge.tsx`, `uploads.tsx`, `admin.tsx`, `auth-guards.tsx`

Several loading states show only a spinner (`<Loader2 className="animate-spin" />`) with no text or ARIA label. Some have text, some don't.

**Instances with text (good):**
```tsx
<Loader2 className="h-6 w-6 animate-spin mr-2" /> {t('settings.loading')}
```

**Instances without text (bad):**
```tsx
// auth-guards.tsx — returns null during loading
if (auth.loading) return null;
```
This is a silent blank screen with no indication to assistive technology.

**Recommended fix:**
1. Always pair spinners with visible or `sr-only` loading text
2. Add `role="status"` and `aria-live="polite"` to loading containers
3. For auth guard loading: show a loading indicator instead of `null`

## 16. Onboarding Stepper Missing ARIA Semantics — LOW

**WCAG Criterion:** 4.1.2 Name, Role, Value (Level A)
**File affected:** `pages/onboarding.tsx`

The multi-step onboarding uses a custom progress indicator with step labels but no ARIA attributes.

**Current gaps:**
- No `aria-current="step"` on the active step
- Steps are `<span>` elements with no role

**Recommended fix:**
```tsx
<div role="list" aria-label={t('onboarding.stepsAria')}>

    <span key={step} role="listitem" aria-current={i === currentStep ? 'step' : undefined}>
      {step}
    </span>
  ))}
</div>
```

## 18. Theme Toggle Has No State Announcement — LOW

**WCAG Criterion:** 4.1.2 Name, Role, Value (Level A)
**Files affected:** `app-layout.tsx`, `landing.tsx`

The theme toggle button shows a Sun or Moon icon but does not communicate its current state (`aria-pressed`) or what action it will perform.

**Recommended fix:**
Use `aria-pressed` and descriptive labels:
```tsx
<Button
  aria-label={theme === 'dark' ? t('a11y.switchToLight') : t('a11y.switchToDark')}
  aria-pressed={theme === 'dark'}
  onClick={() => setTheme(theme === 'dark' ? 'light' : 'dark')}
>
```

**File affected:** `components/account-deletion-card.tsx`

The account deletion flow requires typing "DELETE" to confirm. The input has a `<Label>` but no additional instructions for screen readers about the required format.

## 20. Interactive Cards (Clickable Card Pattern) — LOW

**WCAG Criterion:** 2.1.1 Keyboard (Level A) / 4.1.2 Name, Role, Value
**Files affected:** `settings.tsx`

The Settings page has clickable cards wrapped in `<Link>`:
```tsx
<Link to="/settings/ai">
  <Card className="cursor-pointer hover:border-purple-500/50 transition-colors">
```

This pattern is acceptable because the entire card is wrapped in a single `<a>` element, making it one focusable region. However, nested interactive elements within these cards (if any) would create invalid nested-interactive issues.

**Current state:** No nested interactives found in the settings card links — COMPLIANT.

**Ongoing concern:** If any card later contains a `<Button>` or other interactive, it must be restructured.

## Automated Testing Recommendations

Add these tools to CI for ongoing enforcement:

1. **axe-core** (`@axe-core/react` or `jest-axe`) — automated WCAG violation detection in unit/integration tests
2. **eslint-plugin-jsx-a11y** — lint rules for accessible JSX (alt text, label associations, etc.)
3. **pa11y-ci** — run against the built app for URL-level audits
4. **Lighthouse CI** — track accessibility scores over time

Example vitest setup:
```ts
// test/a11y.test.tsx
import { axe } from 'jest-axe';
import { render } from '@testing-library/react';

it('landing page has no a11y violations', async () => {
  const { container } = render(<LandingPage />);
  const results = await axe(container);
  expect(results).toHaveNoViolations();
});
```
